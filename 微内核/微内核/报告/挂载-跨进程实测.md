## 0. 这一轮换了什么

上一轮只有**一个**调用进程。它能证明「判据穿过外壳还站着」，但证不了「两本账之间会发生什么」——
那正是 README 缺口第 6 条（`Ledger` 没有锁）和第 8 条剩下的那一半（两个进程各写各的）住的地方。
`journal.go` 的注释早就写着「这一条不许被写成已验证」，所以这一轮把它跑出来。

顺带把客户端管道抽成 `tasks/mcp/client.py`（`Kernel` + 判据器 + 「第 1 发」样本一份）：
drive 与 fork 各养一套 JSON-RPC  plumbing，就会有两套「我以为服务端长什么样」，
服务端一改，一个先红另一个继续绿 —— 比没测试更糟。抽完之后 drive 复跑仍是 27 条全绿（行为没变）。

**起点是盘上的真数据**：`报告/样例-真接口两发.jsonl`（kresearch 那一趟真端点，94 条，每条带原像）。

## 2. 分叉的形状（这条是真的坏消息）

A、B 两本都从这 94 条出发，各记一发**自造**的第 3 发（`session=fork-demo`，故意不与真数据混），
A 记 `wire_bytes_in=49`，B 记 `50`：

```
F06/F07  两边都收下：整发落账 47 条，链上共 141 条
F08/F09  两边都报绿：✓ 链自洽（共 141 条，其中 141 条比对过原像）
F10a/F10b 同一个 (session, 发号) 在两本上是两个数：A 那格 49，B 那格 50
F11  前 94 条逐字节相同，第一处分叉在第 95 条
F12  两本的链头是两个不同的数：A=a38a7e1d51e5…，B=41ed544b6209…
F13–F14 第三个进程 C 先收 A 这本 → 绿；换了 B 这本 → 也绿
F15  内核交出去的 10 个工具里，没有一个能判哪本是正史
```

最尖的一处是这两条记录本身：

```
{"seq":128,"session":"fork-demo","actor":"A","step":3,"kind":"model_output:wire_bytes_in","claim":"49",…}
{"seq":128,"session":"fork-demo","actor":"B","step":3,"kind":"model_output:wire_bytes_in","claim":"50",…}
```

`seq`、`session`、`step`、`kind` **四个轴全部相同**，只有 `claim` 与两个指纹不同。
也就是说账上没有任何一格能说出「哪一条是那一发真正发生的那条」——
它们不是「两个 session 撞了号」（那种冲突读侧现在能分开），而是**同一个身份上的两个说法**。

一句话：**哈希链证明「写下来的没被动过」，证明不了「同一时刻只有一本在长」**。
这不是新缺陷，是 README 缺口里那条的实测形状 —— 现在它有数了：一个 `session`、一个发号、两个都绿的答案。

**锚的代价也量出来了**：commit 住整本 141 条只需要一个数 —— 链头那 64 个十六进制字符
（`%d 字节`实测 64）。所以「外部锚」缺的不是数据量，是**谁在什么时候说这个数字是正的**。
这一格还是得人来定（谁签、签给谁），内核给不出，也不该给。

## 3. 挂载过程撞出来的两个真缺陷（都已修）

### D1 读侧只有两根轴，写侧有三根

`alreadyRecorded(session, step, kind)` 按**三个轴**定「同一发」，而
`CellsOf/AbsentKeys/Keys` 只按 `step + kind 前缀` 过滤。一个 session 时看不出来；
这轮两个 session 各记一次第 1 发，`kernel.read_back` 当场回 **`共 40 格`** —— 两发被并成一片。

- 修：`record.go` 三个读侧函数加 `session` 参数（没有「任意 session」的通配 —— 那正是一个会填错的默认值）。
- 钉：新增 `TestCellsOfKeepsTwoSessionsApart`（两本各一发、断言单本读回 20 格、不存在的 session 读回 0 格），
  新增慢闸针 `j10-读侧丢了session这一轴`（把那一行过滤去掉，必须被这根点名的测试接住）。
- 波及：`cmd/kcheck`（6.5 那三条合成 Record 补上 `Session: "kcheck"`，5 处调用补轴）、
  `cmd/kresearch` 2 处、`cmd/mcpkernel` 的 `read_back` 工具**把 session 变成必填**，
  空 session 当场拒。
- 进程外复测：drive.py 第 24 条现在断言 `session=unsaved … 共 20 格` 与 `session=kresearch … 共 20 格`，不再是 40。

### D2 `load_journal` 静悄悄顶掉一本有货的账

载入是**替换**不是合并。上一轮我写这个工具时，当前这本里如果有没 `encode_journal` 出去的条目，
它们会跟着这本一起没了，而返回文本只会说「读回 47 条」。一本账最坏的结局不是被拒，是被静悄悄换掉。

- 修：当前这本非空时必须带 `acknowledge=replace`，否则拒，并报出**会丢几条**：
  `载入被拒：这本账现在有 94 条，载入会把它们换掉（不是合并）。确认要丢就带 acknowledge=replace`
  —— 与 `PayloadUnset` 同一族：一个能靠默认值走通的参数，迟早会被填错的一侧默认掉。
- 顺带把上一轮那条「改 claim 再载入」的判定收紧：现在点名要
  `第 4 条整格指纹重算不符`，并**禁止**出现 `acknowledge=replace` ——
  否则它会因为没签字被拒，那条判定就成了空针（红得对，理由错）。
- 进程外复测：fork.py F13b 量到 C 没签字换第二本被拒（`现在有 141 条`）。

## 4. 找到但**没**修的（记在这里，别读成已解决）

`checkRecord`（`kernel.go:142`）要求 `Actor` 与 `Kind` 非空，**不要求 `Session`**。
所以 `Append`/`RecordInput` 收得下一本没有 session 的账，而 D1 之后 session 是身份的一根轴 ——
两个都没起名字的调用方会共享 `""` 这一本。

这一条是从代码读出来的（不是跑出来的，我没为它造针）。修它等于**新加一条拒收**，
会改变哪些写入进得了门，得配测试、配针、也配一次口径确认 —— 所以留给用户定，不顺手改。
