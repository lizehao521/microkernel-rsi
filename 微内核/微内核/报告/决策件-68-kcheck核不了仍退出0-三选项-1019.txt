== 决策件 #68 · 你回一个数字我就动 ==
【本体一句话】没有 go 的机器上，`kcheck` 把『依赖闭包』那一路降成 `— 核不了`（main.go:58），
  打印用的是 `unknown`（:34 定义，只印 `—`、不 `bad++`），于是退出码仍 0；
  而 `打包.py:322` 断言的正是退出码（那文件里 subprocess.run 只有 1 处）。
  ⇒ 「闸门过了」可以绿在一条根本没核依赖闭包的路径上。

【同文件里已经有一个反例，这是最有力的证据】
  main.go:46 那一族（一个源文件都没扫到）走的是 `unknown(...)` **后面紧跟 `bad++`** —— 
  注释原话写着『核不了不许被读成合格』。也就是说这一条不需要新口径，只需要把同一文件里已有的做法用到 :58 那一支。

【三个选项】
① 给 :58 那一支也 `bad++`（与 :30,46 同形）。行数：1；
   红对照：把 go 从 PATH 摘掉跑一次 kcheck（或 GO_OVERRIDE 指一个不存在的），必须从 `exit 0` 变 `exit 1`；
   正对照：有 go 时仍 `exit 0` —— 两根都要跑，只红不绿等于把闸门改坏了。
   代价：换 kcheck.exe 字节 ⇒ 重编译 + 重打包；**副作用要说清**：没有 go 的机器上打包会当场失败，
        这是诚实的失败（以前是假绿），但会让『在别人机器上跑打包』这条路变硬 —— 要不要接受，是你拍。
② 三列并排印：`✓ N 项 ｜ ✗ N 项 ｜ — 核不了 N 项`，并在 `— > 0` 时把末行改成一句显式警示但保持退出码。
   行数：估 6-10；红对照：读数件里 `—` 计数必须 >0 时才印警示，且断言分母相加 = 总检查项；
   代价：不改『绿在没核的路径上』这件事，只让它看得见 —— 读的人还是得自己看见那一列。
③ 写进交付说明：打包凭据里明写『本次 kcheck 的依赖闭包那一路核不了，PATH 里没有 go』。
   行数：0 行代码（改 打包.py 的文案或 §交付说明）；红对照：造一份 PATH 里没有 go 的环境跑打包，
   生成的 04-kcheck-exe.txt 里必须出现那句 —— 现在它出现的是『退出码 0』。
   代价：这只是把已知失真写得更清楚，不改变闸门语义。

【下次引用 kcheck 的分母只许这么说】（看板 :63 那条已经立了口径）『`✓` 行 N 条，PATH 里有没有 go』，
  别说『40 项/41 项』—— 那个数在没 go 的机器上包含一条根本没核的项。
