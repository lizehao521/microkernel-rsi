## 3. 429：一个把「崩」和「记账」分开的事件

上一版跑的时候端点回了 **HTTP 429**，脚本直接抛异常崩了。那不是端点的问题，是我写的调用方的问题：
崩掉会把「这一发发过、被拒了、要不要再发、要等多久」四件事一起丢掉——而这四件事正是这个内核存在的理由。

现在 `ask()` 把 `HTTPError` 当成一次**计量**处理，那一发照样落账：

```
Failure{Kind:"http", Status:429, Detail:<响应体前 200 字节，已 strip>,
         RetryAfterMs: 有 Retry-After 就记 relayed，没有就 absent（不是 0）}
Streaming=false ⇒ chunks/first_byte_ms/max_gap_ms 三格 absent（被拒在收到内容之前）
WireBytesOut = 真过了网线的请求体字节（发了！）  WireBytesIn = 错误体字节
```

然后按账上那一格等间隔，**重发成新的一发**（发号不覆盖被拒那一发），最多三次。
这一轮真端点没再限流，所以 `fail_turns=0`；但这条支路是在本地假端点上验通的——
它每四请求回一次真 429 带 `Retry-After: 1`，跑出来 `turns=7 fail_turns=1`、15 条判定 0 红。
假端点只写临时目录（`QA_BOOK`/`QA_REPORT` 可外用），**不许覆盖真账**。

## 4. 两处我自己的失误，公开记着

1. **误杀探针。** 我把本地假端点停掉时用了 `taskkill /IM python.exe`（按映像名杀），
   把跑到一半的慢闸进程（PID 9324）一起杀了。那份半途报告已改名留成
   `报告/慢闸62针-挂载轮-被误杀半途.txt` 并在开头标明**不作数**；探针随后重启，这次按 PID 精确停。
   **这是操作失误，不是探针变红。**
2. **写了两条永远不会红的判定。** 上一版 `(1) 本轮未出现非 stop 收尾` 与 `(3) 本轮没出现真故障发`
   是拿我自己生成的字符串 `NOTCOVERED` 去断言 `NOTCOVERED` —— 只能报「过」。
   慢闸那一族专门盯的就是这种空针（判据只能报过时，它就不是判据）。已经改回 `note`，
   只留真会红的断言。对账：真端点那一轮跑出来报的是 14 条，其中 `(3)` 是那条空针，
   去掉后同一轮应是 **13** 条；假端点那一轮报 15 条（7 发落账 + 8 条判定），
   那里 `(3)` 有真 429 数据，是**实打实的判定**，不算空针。
