驱动：`tasks/mcp/llm_probe.py` · 往来全文：`报告/接入LLM-第一发.txt` · 落盘的账：`报告/样例-LLM两发.jsonl`

## 1. 两发真调用（不是夹具）

```
第 1 发  HTTP=200  发出 235 字节 / 收到 478 字节  1389ms
        端点自报模型='agnes-3.0-flash'  finish_reason='stop'
        usage={'completion_tokens': 18, 'prompt_tokens': 93, 'total_tokens': 111}
        原话（49 字节）：我是 Agnes-3.0-flash，由 Sapiens AI 开发。

第 2 发  HTTP=200  发出 391 字节 / 收到 455 字节      ← 把第 1 发的原话真放进 history
        usage 里的 prompt_tokens 涨到 127
        原话（25 字节）：我是 Agnes-3.0-flash。
```

第 2 发是**循环**而不是重复调用：它的历史里带着第 1 发模型自己的话（`history` 那一类段 49 字节），
而它确实把那句话缩短了一半。这是这个仓库第一次「上一发的输出决定下一发的输入」。

内核那边的反应（`kernel.check_call` 先说、再落账）：

```
输入侧：自洽 / 输出侧：自洽
整发落账 47 条（输入侧 20 格 + 输出侧 27 格），链上共 47 条
整发落账 47 条 … 链上共 94 条
✓ 链自洽（共 94 条，其中 94 条比对过原像）
```

## 2. `contract.md` 第 4 节那三个"端点不给"的洞，两个当场被填上

上一轮用 Deep Research 端点接的时候，这三格**仍然缺席**，理由是端点不回：

| 格 | 上一轮 | 这一轮 |
|---|---|---|
| `usage_in` | 缺席（响应里没有 usage 字段） | **93 / 18、127 / 10，出处 = 转述**（分词器在对端，不许记成实测） |
| `usage_out` | 缺席 | 同上，真转述 |
| `endpoint_model` | 缺席（模型没说） | **`agnes-3.0-flash`，出处 = 模型自述**（永远是线索，不是事实） |
| `finish_reason` | 缺席（非流式那一发没说） | **`stop`，且 `finish_said=true`** |
| `retry_after_ms` | 缺席 | 仍然缺席 —— 这一发没断，对端没说要等多久（缺席是对的） |

这一节是本轮最实际的收获，而且它**证伪了"格位表有格永远填不上"这个怀疑**：
那三格不是死格，是之前那个端点没有。接线的人要换端点才拿得到。

## 3. 新发现的洞：**一个量住在两格上，两格可以各说各话，而内核不收这个矛盾**

我把第 2 发的 `tokens`（输入侧）沿用成了第 1 发的数，忘了更新。**账本收下了这个错**：

```
step=2  model_input:tokens    claim= 93（转述自 端点响应的 usage.prompt_tokens）
step=2  model_output:usage_in claim=127（转述自 端点响应的 usage.prompt_tokens）
```

两格说的是同一个物理量（这一发请求的入 token），出处字符串甚至**一模一样**，
一个 93 一个 127，落账时没有任何一格拦它。把两本成本表按不同的键名累加，得到：

```
按 model_input:tokens  累加 = 186
按 model_output:usage_in 累加 = 220
两种分母：tokens+usage_out = 214   ｜   usage_in+usage_out = 248
差额 = 34
```

这正是 README 规矩二那族问题的**镜像形状**：
- 已经防住的：一个键名住两个量（`bytes_out` 那个 6327 vs 11570，靠字段路径撞名判据拦，`j` 族针守着）；
- **今天没防的**：一个量住两个键名（`tokens` 与 `usage_in`）。撞名判据看不见它——两个名字本来就不该撞。

为什么现在才冒出来：`usage_in` 在 Deep Research 端点上**一直是缺席**，两格里只有一格有数，
矛盾在结构上不可能出现。换成一个真报 usage 的对话端点之后，两格第一次同时有数，
差 34 立刻可见。**这条不是接 LLM 带来的麻烦，是接 LLM 才能看见的洞。**

> 补充（写完才做的收尾）：`llm_probe.py` 里那个「第 2 发沿用 93」是我的疏忽，**已经修掉了**
> （现在它从第 2 发自己的 `usage.prompt_tokens` 取数）。证据不必靠重复跑错来保留——
> 它在这份账里：`报告/样例-LLM两发.jsonl` 第 52 条与第 78 条（`step=2` 的 `tokens` 与 `usage_in`）。
> 要说清一件事：**这份样例是修复之前那一次跑出来的账**，故意没覆盖 —— 它留的就是那个错。
> 修复后同一脚本再跑一遍（2026-10-13，8 条判定仍全绿），第 2 发得到 `tokens=127 / usage_in=127`。
> 修的是调用方的错；**内核拦不住这一对**这件事与谁犯错无关，仍然开着。


要不要修、怎么修，是口径问题，我不替你定。三个候选：

1. **钉成一条判据**：两侧都落账且都可判定时，`tokens` 必须等于 `usage_in`，不等就整发拒收。
   代价：装配时刻与响应时刻本来就是两个时点，将来「先估后转述」这种正确用法会被自己的判据拒。
2. **允许不等，但必须说清关系**：谁不同谁必须带 `Why`，并让账上有一格写明"这是装配时的估算，端点后来报了 127"。
   代价：多一格、多一个 owner 要复核。
3. **只留一格**：`tokens` 改成只有估算那一档能用，端点报了 usage 就不许再填输入侧那一格。
   代价：装配时刻的记录会丢——那正是可复用前缀与预算回夹要看的。

我的倾向是 2，因为这三格本来就不是同一个时点的观测，硬钉成相等会把"估算"这一档挤成假数。
但这一条我不动手：它是**契约扩张**，而且 `RecordCall` 里加跨侧判据会让"一格一量"这条不变量多一个 must-check。
