# 待定形状：「两个状态」与「格式那一格」（缺口 10）

日期：2026-10-13 · 状态：**已按读法 B + 3a 落地（封板轮）** · 下面这份从"草案"变成了"落地记录"，
未选的那几条（读法 A、3b）与推翻我的那处（`measured`→`relayed`）都留在原处不删，
免得下一次有人以为这是拍脑袋改的。落地后的实际形状：

| 本文当初的问号 | 落地的样子 |
|---|---|
| 「两个状态」两根轴 | `FailKind.MayCarryStatus()`（output.go，与 `RetrySame()` 同住一处），`Failure.check()` 那两条按类别的互核删除 |
| `fail_detail` 出处 | 跟着那张表：收到过响应 ⇒ `relayed`（对端原话现在名正言顺进账） |
| `fail_status` 出处 | 从 `cells.go` 写死的 `BasisMeasured` 改成跟着同一张表；不许带码的那一类与没故障的发是 `absent` 带理由 |
| 「格式那一格」 | 加了 `wire_format` + `wire_format_said`，出处 `relayed`，装**对端自报的原字**（`chat.completion` / `chat.completion.chunk`），不是我们自己编的 `openai-chat/v1` —— 走的是本文 §3.1 改口之后的那份 |
| 额外撞出来的（本文当时没预见） | ④ `notice_sent` 钉在段表上、⑤ `Cut.RefCall` 可核引用 —— 都是落地那一轮被真跑逼出来的，见 `报告/挤历史-判生死.md` |

仍然没解决的：**类别那一格没有第二根轴能反证它**（把 `config` 谎报成 `http` 仍然走得通），
以及"三把指纹单位不同、连不回原文"那一半（账上不存原文，见本节第 12 条）。

用户给的口径是「增加两个状态；openai 格式增加一个」。「两个状态」有两种读法，
落地形状完全不同，这里各画一份，并附今天刚量到的证据。

## 0. 先看那条被证伪过的旧判据

`output.go` 的 `Failure.check()` 今天写着：

```go
if f.Kind == FailHTTP && f.Status == 0  { 拒 }   // http 必须带码
if f.Kind !=  FailHTTP && f.Status != 0 { 拒 }   // 别的类别一律不许带码
```

第二行被一发**真 401** 撞开了：`FailConfig` 的三种成因（密钥错、模型名不存在、参数非法）
在 HTTP 上**全都带 4xx**，而这一条不许 `config` 带码（`报告/假key一发-401.md` 第 2、3 节）。
而 `fail_detail` 的出处**还跟着状态码走**（`Status≠0 ⇒ relayed`，否则 `measured`），
所以留码就得让类别说谎，抄原话就会被标成"我们量的"。

**同一行又被第二发撞开了，那一发不花钱**（`报告/协议档一发-200坏body.md`）：
本机假端点回 **HTTP 200 + 断掉的 body**（`protocol` 那一档唯一的真形状），
照实装配（`Kind=protocol`、`Status=200`、`Detail` 放对端原字节）被内核**整发拒收**，
原话是「protocol 不是 http 那一类，却带着状态码 200」—— **47 格全丢**，
连与"是不是 http"毫无关系的 `wire_bytes_in=46` 一起没了（那本 jsonl 是个 0 字节的空文件）。
换成让步装法（码归 0、Detail 换成我们自己的判定句）就过了：47 条、链自洽、19 判定 0 红，
但账上留下一格 **`fail_status` = measured `0`** —— 而 HTTP 没有 0 这个码。

**所以这条判据不是"401 这个特例 unlucky"，是它用一个类别名冒充了另一根轴**，
两个独立实例（`config`/401、`protocol`/200）现在都在。清点过的存量：
九本在册样例账里 **27 发落账、27 个 measured `0`、无一例外**，其中 **22 发根本没有故障** ——
一次成功的往来也写着"量到状态码 0"。成因比互核更深一层：`cells.go:120` 把那一格的出处**写死**成
`BasisMeasured`，调用方结构上就没法把它记成 absent。

**今天真正学到的分界线是另一条**：`transport` 能原样重发却**永远没有**状态码（压根没收到响应），
`config` **一定有**状态码却**不许**原样重发（`报告/假key一发-401.md` 第 6 节）。
也就是说：「能不能带状态码」问的是**有没有收到对端响应**，
「要不要重发」问的是**原样再发有没有用** —— 这是两根独立的轴，今天被挤在 `kind` 一根轴上，
只在 `http` 那一档恰好重合，所以那条判据一直没被证伪过。

## 读法 A：「两个状态」= 取值表再加两档

把 `FailKind` 那 7 档拆细，新增两档，例如：

| 新档 | 收的是什么 | RetrySame | 带状态码 |
|---|---|---|---|
| `rate_limited` | 429 / 408 / 5xx：对端忙或断了 | 有用 | 必须带 |
| `rejected` | 4xx：密钥、模型名、参数、格式不合法 | 没用 | 必须带 |

代价很实在，我不建议：

1. 它与现有两档**重叠** —— `http`（"408/425/429/5xx"）与 `rate_limited` 说的是同一批数，
   `config`（"密钥错、模型名不存在、参数非法"）与 `rejected` 也是。
   重叠的取值表就是本包第 8 节里那条老病的翻版：同一件事有两个档，读的人不知道归哪个。
2. `failKinds` 那份表是 `RetrySame`、报红文案里「7 种」这些数唯一的来源，加档会连着改一片；
   而**加档解决不了那根真正的轴**：`transport` 仍然没有码，`config` 仍然有码，
   只是换了名字继续互斥。
3. 取值表照搬的是证据源 `runloop internal/ctxbuf` 那份枚举（README 第 7 节），
   擅自扩档等于让内核的表比证据源多两格，而这两格没有出处。

## 读法 B（改写版）：「两个状态」是两根轴，而**第一根不需要新格**

我把三本在册的故障账并排读出来（真端点那三轮 + 一发空端口）：

```
发  fail_kind           status  wire_in  wire_out  sent      finish       says
1   config（真 401）      0       118      662       发出去了    （空的）      0
1   transport（空端口）    0       0        662       发出去了    （空的）      0
1   （正常）              0       586      662       发出去了    tool_calls    0
3   malformed_action      0       428      1180      发出去了    length        0
4   malformed_action      0       2849     1321      发出去了    length        1
```

看头两行，**账上此刻正在自相矛盾**：同一发写着「收到了 118 字节」，又写着「没有状态码」——
后者不是事实，是旧判据逼出来的（`kind≠http ⇒ status=0`），而没有任何判据把这两格对起来。

于是「两个状态」的正确落法是这两根轴，**都不必新增布尔位**：

| 轴 | 谁在答它 | 今天 | 该改成 |
|---|---|---|---|
| **有没有收到对端响应** | 该由一张 `FailKind → 许不许带状态码` 的小表答（与 `RetrySame()` 同处住，一处定义） | 没有判据把它和 `status` 对起来；旧判据用「是不是 http」冒充这根轴 | `status≠0 ⇒ Kind ∈ 白名单`（`http`/`config`/`protocol`/`malformed_action` 这一类"对端回了话"的）；`transport`/`budget` 按定义没收到，继续不许 |
| **原样重发有没有用** | `FailKind.RetrySame()`（类别的函数，一处定义） | 已经在答，且答得对 | 不动 |

**为什么不用 `wire_bytes_in` 当那根轴的 owner**（我先想过这条路，被自己的数据挡回来了）：
那一格数的是**响应体**的字节。真 401 那一发它给了 `118`（对，收到了话），
空端口那一发给了 `0`（对，没收到）—— 两条都对得上；
但一个**没有 body 的响应**（204、或某些网关的空 4xx）会给出 `wire_bytes_in=0` 而 `status=4xx`，
判据就会把一条真实的拒绝当成不可能发生而拒收。
「收到了几字节」与「对端有没有回话」是两个量，共用一根轴就会在边界上互相打脸 ——
这正是规矩二那一族。字节那一格继续只管字节，能不能带码由那张类别白名单答。

我上一版草案里准备加的 `Failure.Answered` 布尔位 —— **删掉这个念头**：
它是 `wire_bytes_in` 的第二个名字。本包为这一族已经有过两次现场
（`tokens` 与 `usage_in` 同一个量两个键名、实测差 34；`bytes_out` 与 `wire_bytes_out` 迁移期共用过名字），
不该再添第三次。

`fail_detail` 的出处跟着**第一根轴**改（收到响应 ⇒ `relayed`，否则 `measured`），
不再跟着 `Status≠0` —— 这样 config 那一发抄对端原话也能名正言顺标 `relayed`，
今天那个"抄原话就被标成我们量的"的连带毛病一起消掉。

**净新增键名：1**（只有下面那格 `wire_format`）。`FailKind` 那 7 档不动，
`contract.md` 那张表只长一行，`RetrySame`/`failKinds` 那一片连带的文案都不用改。

一个已知的洞，写在脸上而不是藏起来：`wire_bytes_in` 今天量的是**响应体**的字节。
所以对端回了个**没有 body 的响应**（例如 204，或某些网关的空 4xx）时，
账上会是 `wire_in=0` 而 `status≠0` —— 正好触到上面那条新互核。
这一格该不该把响应头一起数，是 README 里本来就挂着的那条待定项（「header vs body bytes」），
两条要一起定，不能各定各的。

## 3. 「openai 格式增加一个」：这一格确实是新量，不是第二个名字

今天有一件**硬证据**说明这一格不是装饰：模型上一轮吐出的那条参数被截的提议，
我原样接进历史发回去，**对端自己回了 400**：

```
{"error":{"message":"… OpenAIException - Assistant tool call ***.arguments must be valid JSON."}}
```

也就是「能不能把模型的上一句话原样喂回去」不是我们的选择，是**这套往来的格式规定**（第 4 轮那份报告的 §3）。
而账上今天没有任何一格说这一趟是按哪个格式谈的 —— 端点自报的只有模型名（`endpoint_model`，档位 `model_says`）。
`tools/list` 那一头也踩过同一族：外壳里写着「入参键名就是 Go 的导出字段名，没有独立 wire 形状」，
而那句是注释，没有格（README §2.2 末段）。

## 3. 「openai 格式增加一个」：这一格确实是新量，不是第二个名字

### 3.1 先把我上一条推荐推翻掉

上一条草案我说：格式是对端规定的，但**对端从没把这个字符串告诉我们**，
所以那一格只能记 `measured`（"我按 openai-chat/v1 发"），记 `relayed` 就是转述对端没说过的话。

**这句被一发真调用打回了**（`报告/响应头自报.txt`，2026-10-13，未流式一发，HTTP 200）。对端不但说了，还是在两个地方各说了一遍：

| 出处 | 对端自己的字 |
|---|---|
| 响应体顶层 `object` | `chat.completion` |
| 响应头 `x-new-api-version` | `master-cn-24eea8e18c2bc40aa0c711100d4c6ee58c51fcf1` |
| 响应头 `x-litellm-model-name` | `agnes-3.0-flash` |
| 响应头 `Content-Type` | `application/json` |

所以 `relayed` 那一档**能用**：`BasisRelayed` 要的"Source 指得出谁算的"，这里指得出 —— 对端在 body 里亲手写了 `chat.completion`。
我上一条推荐的 `measured` 反而要说谎：它会把"对端自报的字符串"标成"我们量的"，正是 `endpoint_model` 那格已经躲开的事。

### 3.2 但有一个不对称必须写在脸上

对端那个 `object='chat.completion'` 描述的是**它这次响应**的对象类型，**不是它接受什么样的请求**。
我们的请求侧按哪个格式谈，对端从没说过 —— 那是从端点路径 `/v1/chat/completions` 和它回 400 那句
`OpenAIException - Assistant tool call ***.arguments must be valid JSON` 倒推的（第 4 轮报告 §3）。

于是这里有**两个量**，不是一个：

| 量 | 谁知道 | 档位 | 值的形状 |
|---|---|---|---|
| 我们这次按哪个格式发 | 只有我们自己（驱动里那行接线） | `measured` | `openai-chat/v1` |
| 对端自报它回的话是什么格式 | 对端写在 body 顶层 | `relayed`，Source = 响应体 `object` | `chat.completion` |

它们**会不一致**，而且不一致正是有用的那格 —— 这一句我没有停在推断上，跑了一支对照探针
（`tasks/probe/wire_format_probe.py`，同一个 8-token 的问题各发一发，实测记录在 `报告/格式自报-流式对照.txt`）：

| | stream=False | stream=True |
|---|---|---|
| 对端自报的 `object` | `chat.completion` | **`chat.completion.chunk`** |
| `Content-Type` | `application/json` | `text/event-stream` |
| 响应头**条数** | 18 | **12** |
| `x-new-api-version` | 在 | 在（同一个 commit） |
| `x-litellm-model-name` | 在 | **不在** |
| `x-litellm-response-cost-input/output/tool-usage` | 在（三个 0.0） | **都不在** |
| `x-request-id` / `x-trace-id` | 在 | 在（但另一串，且两者同值） |

三个结论，都是量出来的不是推出来的：

1. **那一格每发都可能变** —— 它对端在两种格式下自报两个不同的字，所以它是观测，不是常量。
   这正面回答了"这一格凭什么占一个键名"：今天的 46 格里没有任何一格能记下
   "这一发我们按流式谈、对端也确实按流式回了话"这件事 —— `streaming` 只说我们的开关，
   `chunks` 只数我们收到的帧，两者都**没读过对端自报的身份**。
   它们互相打脸的场景（我们发 `stream=true`、对端回一个 `object='chat.completion'` 的整包 JSON）
   现在没有任何判据接得住，而有了这一格才谈得上钉它。
2. **响应头在对端两种格式下不是同一份**（18 条 vs 12 条，且缺的正是对端自报的模型名与成本）。
   所以"能不能一直从 header 取某个自报值"这个前提**不成立** —— body 里的 `model` 两发都在，
   header 里的 `x-litellm-model-name` 流式那一发没有。这一条对 `endpoint_model` 的取数路径有直接影响，
   写进 §3.5 的待定里一起定。
3. `x-new-api-version` 在两发里给出**同一个 commit 串**，它是对端网关版本的稳定出处 ——
   但账上没有那一格（见 §3.5）。

按规矩二（同一件事不许有两个名字，`Answered`/`wire_bytes_in` 那一族），这两个量**不能共用一个键名**。
所以这一格有两种落地，都要你点头才动判定文件：

| | 加几格 | 记什么 | 我不加的那一份怎么办 |
|---|---|---|---|
| **3a 只加对端那一格**（我现在的推荐） | 46→47：`wire_format`，`relayed`，装 `chat.completion` 原字 | 对端自报的格式 | 我们自己的接线常量不进账 —— 它住在驱动的源码里，是写死的，不是每次量出来的 |
| **3b 两格都加** | 46→48：再加 `wire_format_says` | 两侧都在账上，不一致能直接读出来 | — |

我推 3a：`endpoint_model` 那一格走的就是"对端自报的原字 + 可指名的 Source"这条路，
`wire_format` 照它办最省，而我们自己的接线是个常量不是观测 ——
为一行写死的代码开一格，读账的人会以为它每发都可能变。
3b 只在"要让账本自证请求侧口径"时才值得，那属于缺口 11/12 那一族（已定：缓到接 runloop 一起）。

顺带把另一条不加格的做法留在这儿对比：把格式塞进 `session` 名（`openai-chat-v1:qa`）。
我不建议 —— 那等于把口径藏进自由文本，正是 README 第 8 节缺口 10 里
"401 只能住散文"同族的毛病，而且 `kcheck` 的读侧三入口是按 `session` 整串匹配的。

## 3.5 同一发响应头里还查出三个"无处可放"，附采集点缺失

那一发抓到 18 个响应头，其中四条**对端明确自报、账上却一格都装不下**：

| 对端给的 | 现数 46 键里谁能收 | 实测结论 |
|---|---|---|
| `x-request-id` / `x-trace-id`（两发各一对，同值不同串：`7b38e803…` / `b8cae19d…`） | 无 | 想挂"这一发在对端那边叫什么"没有格 |
| `x-new-api-version: master-cn-24eea8e18c2bc40aa0c711100d4c6ee58c51fcf1` | 无（`endpoint_model` 只收模型名） | 对端网关的**版本**进不了账；两发同值，是稳定出处 |
| `x-litellm-response-cost-input/output/tool-usage = 0.0` | 无 | 对端自报的成本与 `cost_countable`（我们算的）是两个来源，混不得 |

新增一条**由对照探针查出来的**（上面第 2 点）：**同一份自报信息在两种格式下不是都在**。
`x-litellm-model-name` 只在非流式那发出现，流式那发没有 —— 而 `endpoint_model` 那一格今天吃的是
**响应体**里的 `model`（两发都在，所以还没出事）。这条要留在待定里是因为：
如果以后改从 header 取，流式那一发就会**静默变成空**，
而按本包的规矩，"没读过"与"读了是空"读起来一模一样 —— 这正是规矩二防的那一族。

更要紧的是：**这三条不是"没开格"，是连采集点都不存在** —— `urllib` 那侧我们只读了 `resp.read()` 的 body，
`resp.getheaders()` 从来没碰过（除这一支临时探针和 `tasks/probe/wire_format_probe.py`）。这正是 contract §4 那一族现行犯：
一个量从没被读过，账上就永远没有它，而"没读过"与"读了是空"读起来一模一样。
这一条我不建议现在就开格 —— 它该和 header/body bytes 那条待定项一起定
（见上面 §2 末段那个洞：`wire_bytes_in` 到底数不数响应头）。
