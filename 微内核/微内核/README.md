# agentkernel —— 模型输入/输出元数据微内核

一句话：**把「一发模型调用」的两侧账做成一个独立的、只依赖标准库的 Go 包**，
让每一格都自带「谁算的」和「量到了没有」，并且缺依据的写入进不了门。
它是**追责与拦编数**的件，不是让模型答得更准的件——2026-10-15 一场 8 题盲测（纯模型 8/8、
带本内核 6/8）量到的正是这条边界：那 8 题里没有不实报账可对质，工具不在答案的证明路径上。
把它当"能力增强"卖，别人就会拿答题来考它，然后失望——这句是文档要背的锅，写在第一屏。

它不调度、不联网、不执行工具、不写磁盘。那些是 Agent 框架的事。
依赖只有一个方向：**框架 → 内核**。
**这条方向的守法则要说准**：格位表、逐格出处、链的三态都是机器判的（见下面「怎么核」），
但"`package kernel` 不 import `net/http`、不写磁盘"目前**只有目录约定与这句散文守着**——
`isolate.go` 只分 自有/三方/标准库，而 `net/http`、`os` 都算标准库，"0 泄漏"抓不到它哪天联网。
已立案（#26），补它要改闸门、让整轮凭据再过期一次，所以排在 v1.1，不写成已守护。

## 1. 先做什么

两条命令，都要跑：

```
go test ./...          # 全部判据（单元测试）
go run ./cmd/kcheck    # 闸门：逐节核，每个数由它自己印
```

- **前提：`go` 得在 PATH 上。** 每台机器它装在哪不一样，本机当前是
  `/c/Users/Admin/sdk/go/bin`（Go 1.27.2），Git Bash 里先跑
  `export PATH="$PATH:/c/Users/Admin/sdk/go/bin"` 再跑上面两条。
  工具链真够不着时（例如直接跑一个编好的 `kcheck` 二进制），它的依赖闭包那一栏会印「核不了」——
  那既不是绿也不是红（见 5.1）。慢闸还要 Python 3（只用标准库），本机在
  `/c/Users/Admin/sdk/py314/python.exe`。
- **看哪一格**：`go test` 看每个包一行 `ok`；`kcheck` 看最后一行 ——
  `✓ 全部通过` 或 `✗ N 项没过`，退出码非 0 = 有项没过，以退出码为准。
  输出里 `✓` 是过了、`✗` 是没过了、`—` 是不判定或核不了，数由它自己印，不用手数。
- 控制台不是 UTF-8 的话（Windows 的 GBK 控制台），把输出重定向进文件再读，否则 ✓/✗ 会变成乱码。
- **要数就读 `kcheck` 印出来的那几行。这份 README 不写会漂的数** ——
  格数、字段数、文件数、import 条数每个 commit 都会漂，而漂了的数比没有数更有害。
  带出处的历史读数（例如规矩二里那次 6327 → 11570 的实测）例外：它们是证据，不是当前状态。

几个内部词，后文不再逐个解释：

- **一发**：一次模型调用（请求 + 响应）；「发」是它的量词，发号 `Call` 从 1 起。
- **格 / 键名表**：`Cells()` 交出来的账目条目（键名 + 值 + 出处 + 字段路径；转述与估算那两档还带来源 `Source`）；全部格子的清单叫键名表。
- **出处 / 档**：`Basis`，「这一格是谁算的」的分档 —— measured（我们量的）、relayed（转述别人算的）、
  estimated（估的）、model_says（模型自述）、absent（这一发没有这一格）、unset（忘了填，门口就拒）。
- **缺席**：这一发没有这个数 —— 要么结构上压根没有（非流式那一发没有首帧等待），
  要么对端给了数、被判成不可信而没收（`Distrusted`：留住理由与那个被拒的数）。
  与「量到了 0」「忘了填」是三件事（规矩一）；两种缺席在渲染上也不共用同一句话。
- **死格 / 幽灵键**：字段在、却没有一格替它落账（死格）；一格指着不存在的字段或方法（幽灵键）。两者都有机械判据。
- **回夹 / 刀**：装配出来的请求体超了上限，就把内容额度收小重装配；每收小一次叫一刀（`Budget.Clamp`）。
- **桩**：一段原文被折叠之后留下的占位，带着原文指纹能核回去。
- **证据源那个仓库**：同目录那个已经跑过真端点的 `runloop`，本包字段表是从它逐格挖出来的（第 7 节）。
- **擦码器**：框架那一侧把密钥一类抹掉的脱敏组件，内核 import 不到它（缺口第 5 条）。
- **快闸 / 慢闸**：`kcheck`（秒级）与 `kprobe`（逐根针在临时拷贝里制造破坏、要求被点名的判据接住，分钟级），见第 5 节。
- **判据**：一条能真的红的检查。红不了的承诺是散文，不算。
- **一份判据（`checkRecord`）**：「一条记录能不能进账」在全包只有这一份判据 ——
  账本门口 `Append` 与翻译那一步 `plan` 都从它读；「plan 放过的，commit 一定收」靠它成立（第 2 节）。

## 2. 它管哪两件事

| | 是什么 | 类型 | 一句话 |
|---|---|---|---|
| 输入侧 | 一发请求**装配完之后**，关于我们发了什么 | `InputMeta` | 段表、字节、token、预算口径、被挤掉的段（逐项留痕）、那句知情通知 |
| 输出侧 | 一发响应**回来之后**，关于我们收到了什么 | `OutputMeta` | 收尾原因、token 用量、过网线字节、流式那三格、工具提议、故障分类 |

两侧的格子都从 `Cells()` 出去，每格带着键名、值、出处（谁算的）与字段路径；
转述与估算那两档还必须带来源（`Source`）—— 说不出转述谁的那一格，和模型自述在证据上没有区别。

**元数据怎么进账本**：`Cells()` 交出来的是值，真正把它们写进那道出处闸门账本（`Ledger`，一条哈希链）的入口住在 `record.go` —— `RecordInput` / `RecordOutput` 各写一侧，`RecordCall` 把一发的两侧一起写，**逐格一条**：键名表交出来的每一格，各成一条账本记录，条目名拼成 `<kind>:<key>`（例如 `model_input:content_bytes`）。每条记录带着 `Claim` 与 `Payload`：`Claim` 是那一格的人话版本（短，给人读），`Payload` 是原值序列化后的字节（全，给第三方重算、并被指纹覆盖）。`Claim` **永不为空**：空的 `Claim` 在账上与「这一格没写」长得一样，而读的人分不清「值是空串」与「没有值」—— 那正是这个包要消灭的「缺席长成 0」那一族，只是换到了字符串上；空值一律渲染成非空的人话：空串、空字符串表与渲染出来只有空白的值落成共用常量 `emptyClaim` 那句话，每张空表落成一句点出自己名字的零话 —— 空的发送顺序表与空的裁剪表是两个量，不许共用一句「0 段」。
**但「一张没交的名单」不是空表，它不渲染零话。** `Cuts` 这个键没交 ⇒ 解码后是 nil（交一张空表 ⇒ 非 nil 空），
那三档在键名表这一层就带 `BasisAbsent` 交出去、落成一句「没交这一档的名单，不是空表」，原像是 `null` 而不是 `[]`；
`basisOf` 只放三态量与 nil 名单进 `absent` 那一档，别的东西报缺席当场拒。
这一条 10-19 之前是反的（nil 与空表都被抹成 `measured 0 段`，见 contract.md §4 第四条与看板 #66）。

刻意不做的一种形状是**「写半发」**：一发要么整发逐格落账，要么整发拒收，不留半截记录。因为半截记录会让下游那类「不拿半截历史续跑」的守卫拒掉整条链 —— 而根因其实在我们这边（证据源那个仓库真踩过一次），被怪罪的却是整条链。

这个保证是**结构性的**，不是「靠 `Check()` 恰好挡住」的涌现性质。它站在两根柱子上：

- **先全部翻译、一条都不写。** 落账分两步：`plan()` 把一侧（`RecordCall` 是两侧全部）的格子逐格翻译成记录，全译通了 `commit()` 才逐条进链。`Check()` 不过、翻译中途被拒（一格翻译不成账、值序列化不了、撞上「这一发已经记过」），都是整发拒收、并把这次拒收也计进拒收数（拒了也要看得见）。将来谁加一种新格子或新出处档，让 `Check` 过而翻译拒，那一发也只会整发进不了账，不会在链上留半截。
- **一份判据，两层共用。** 「一条记录能不能进账」在全包只有 `checkRecord` 一份判据：账本门口 `Append` 从它读，`plan` 对每条翻译好的记录也先跑它一遍。于是「plan 放过的，commit 一定收」是结构推论，不再依赖「`Check()` 恰好挡掉了所有会让 `Append` 失败的形状」那条隐式契约 —— 隐式契约会漂，这一条不会，因为两层读的是同一份代码。两根柱子在 `go test` 里各有判据站岗：`TestNoHalfCallEvenWhenTranslationFailsLate` 守次序，`TestPlanRefusesWhatAppendWouldRefuse` 守共用判据。

第二根柱子的反面也要说清：`commit` 自己仍然是**逐条**进链，不是原子操作 —— 万一它中途失败，已写进去的那些会留在链上（这个行为被 `TestCommitAcceptsEveryShapePlanTranslates` 钉住，不靠嘴说）。但对 `plan` 交出来的记录，「中途失败」在结构上到不了：`Append` 唯一的拒收理由就是那份 `checkRecord`，而 `plan` 已经逐条跑过同一份。所以**「半发已被消灭」在三个公共入口上成立**（`RecordInput` / `RecordOutput` / `RecordCall`），理由是共用判据，不是运气；将来谁给 `Append` 加一条 `checkRecord` 没镜像的判据，`TestPlanRefusesWhatAppendWouldRefuse` 与 `TestCommitAcceptsEveryShapePlanTranslates` 那两条会红。

**同一发同一侧只许记一次**：对同一发调两次 `RecordCall`，若都收下，账本会写下两套条目而哈希链**照样自洽** —— 链只证明「写下来的没被动过」，证明不了「不该写的没写」；任何按键名扫账本的分析层会把这一发的字节、token、成本加两遍，而账上没有一格说得出「这两套其实是同一发」。所以去重由门口拦、不靠读的人：`plan()` 落账前先查 `alreadyRecorded`（同 session、同发号、同侧有过记录就拒），重复记直接拒收并计入拒收数。这道闸的视野是**一个内存账本**，而且每记一笔都全账本线扫一遍；跨账本的那一半与长趟的代价都是缺口（见「已知缺口」最后一条）。

### 2.1 账本的字节格式住在 `journal.go`（落盘这件事被拆成两半）

「落盘」一直写着是框架的事，但它其实混着两件该分开的事：**字节的格式**与**把字节放到哪**。
前者如果不由内核拥有，框架最自然的写法（`json.Marshal(entry)`）就会**默认丢掉原像** ——
`Entry.Payload` 带着 `json:"-"`，于是那 47 条落进 JSONL 之后，第三方拿到 `PayloadH` 却重算不出原值，
而「别人能按同一规则重算」正是这本账全部的卖点。
所以现在内核拥有格式（`MarshalJournal` / `ReadJournal` / `LoadLedger` / `CheckChain`），
**仍然不碰磁盘** —— 这一份文件连 `os` 都没有 import，交出去的是 `[]byte`，
写进哪个文件、何时 fsync、要不要压缩，仍然住在框架那一侧。

三件事由这一层站岗：

- **带不带原像必须有人签字。** `PayloadMode` 的零值是 `PayloadUnset`，编解码门口直接拒 ——
  与 `Basis` 同一个道理（规矩一）：一个能靠「忘了填」走通的参数，迟早会被填错的一侧默认掉。
  选了 `PayloadIncluded` 却解不出原像，与选了 `PayloadOmitted` 是两种完全不同的账，
  不许在字节流上长得一样（所以空原像编成 `payload_b64:""`，没带原像是**省略这个字段**）。
- **「没有原像」与「内容被动过」是两句话。** 这是这一层存在的理由。
  反面（改之前的真实形状）：读回来的 `Payload` 是 nil，`Verify()` 里那句 `sum(nil) != PayloadH`
  于是把 47 条**完好无损**的账全指控成「内容被动过」—— 下一次真篡改就淹在这堆假警报里。
  所以现在 `ChainReport` 是三态的（过 / 没过 / 核不了），`Decidable()` 对「核不了」报假，
  而它的 `String()` 在那一栏打 `—` 不打 `✓`：第三种答案不许长得像绿。
- **读回来要能接着记，而且去重闸看得见旧账。** `LoadLedger` 把条目真填进 `Ledger.docs`，
  于是进程重启后把同一发再记一遍会被 `alreadyRecorded` 拒掉（缺口第 8 条里跨重启那一半由此关上，
  剩下那一半仍然开着 —— 见下面第 8 条）。

`Verify()` 现在只是 `CheckChain()` 的一个调用方 —— 判据一份（规矩三），
所以「内存里的账本」与「从盘上读回来的账本」不会漂成两套规则。

### 2.2 挂成一个进程（`cmd/mcpkernel`）：「没有调用方」这条第一次能测

挂法是把内核包成一团 MCP（newline-delimited JSON-RPC over stdio）服务，共 10 个工具。
它不新加任何判据 —— 每一格都走 `Check()` / `RecordCall()` / `CheckChain()` 那几扇同一个门口，
外壳只解 JSON、只排版。**依赖方向没变**：`package kernel` 至今没 import `net/http`，也没 import 过 MCP。

实测见 `tasks/mcp/drive.py`（27 条判定，全文往来落在 `报告/挂载-MCP-往来.txt`），效果是这四条：

- **格位表可以现场要。** `kernel.celltable` 回「当前 49 格（输入侧 20 + 输出侧 29）；唯一键名 48 个」（这一轮从 47/46 长过来的，见缺口 10 那一节）——
  接入方不必再抄 `contract.md` 第 3 节那张表，也就没有抄错这一说。
- **拒收穿过外壳照样是拒收。** 拼错的键名声明、非流式写成分帧 0、预算挡下却报字节没数到、
  两侧发号对不上 —— 四次当场红，`被拒的写入 4 次` 计入合计，链上仍是 47 条不多一条（那一轮一发 47 格）。
- **「断开即失」的一半由调用方收回去。** `kernel.encode_journal` 只交字节（**不写盘**），
  `kernel.load_journal` 把字节读回来顶掉这本账 = 这个进程重启了一次；
  重启后同一发再记仍然被去重闸拦下。不带原像读回来时它报 `— 核不了`，不喊篡改、也不打勾。
- **读者声明第一次有活干。** `kernel.readers_report` 之前一直是空的（缺口第 1 条），
  现在有一个真读者声明了一格，输出侧从 27 格没人读变成 26 格。

要说清的代价：账活在**这个进程的记忆里**；`Ledger` 没有锁（缺口第 6 条），所以这里刻意**一次只处理一条请求**；
`InputMeta`/`OutputMeta` 没有独立的 wire 形状，工具入参的键名就是 Go 的导出字段名 ——
把它写成 schema 会是假绿，所以 `tools/list` 里只写着字段清单，谁都没核过它。

### 2.3 挂第二轮：三个进程、同一份起点，撞出两个真缺陷

`tasks/mcp/fork.py` 起**三个**进程，起点都是盘上那 94 条真端点账（`报告/样例-真接口两发.jsonl`）。
正面那一条：`✓ 链自洽（共 94 条，其中 94 条比对过原像）` 由**两个互不知情的进程**各算一遍算出一样的结果 ——
「别人能按同一规则重算」这句话第一次不是在同一进程里自证。

坏消息也是量出来的。A、B 从同一份 94 条出发，各记一发自造的第 3 发（一个记 `wire_bytes_in=49`、一个记 `50`）：
两本都 141 条、**都报绿**、同一个 `(session, 发号)` 给出两个数，前 94 条逐字节相同、第 95 条起分叉、两个不同的链头。
**哈希链证明「写下来的没被动过」，证明不了「同一时刻只有一本在长」** —— 缺口里那一条现在有了数：
锚要 commit 住整本 141 条，只需要一个 64 个十六进制字符的数（链头），缺的是「谁在什么时候说它是正的」。

两个缺陷当场修了（细节见 `报告/挂载-跨进程实测.md`）：

- **读侧少一根轴。** 写侧 `alreadyRecorded(session, step, kind)` 用三个轴定「同一发」，
  读侧 `CellsOf/AbsentKeys/Keys` 曾经只认 `发号 + 侧` —— 两个 session 各记一次第 1 发，读侧回「共 40 格」。
  现在三个读侧函数都带 `session`（不给「任意 session」那种通配：那正是一个会填错的默认值），
  由 `TestCellsOfKeepsTwoSessionsApart` 与慢闸针 `j10` 钉住。
- **`load_journal` 会静悄悄顶掉一本有货的账。** 载入是替换不是合并；现在当前这本非空时必须带
  `acknowledge=replace`，否则拒，并报出会丢几条（与 `PayloadUnset` 同一族）。

### 2.4 挂第三轮：接一个真对话端点，三轮共 13 发真调用

`tasks/mcp/llm_probe.py`（2 发）、`qa_loop.py`（6 发）、`tools_probe.py`（5 发）经同一个挂载把
OpenAI 兼容端点 `agnes-3.0-flash` 的往来落账。三轮各拿各的东西，报告分别是
`报告/接入LLM-第一发.md`、`报告/答题循环-六发.md`、`报告/工具提议-实测.md`。

**「没有死格，只有还没接的端点」这一句现在有数了。** 上一轮只能拿 Deep Research 那个端点做证据，
它不给 usage、成功也不给 Retry-After，于是 `usage_in` `usage_out` `endpoint_model` `finish`
这四格只能说「形状对、没人填」。对话端点一接上，四格当场有真数（`relayed`／`model_says`），
`chunks` `first_byte_ms` `max_gap_ms` 三格第一次拿到**这一路**的实测帧数（66 帧、618 ms、299 ms）。

三件只有真跑才会翻出来的事：

- **内核第一次当面拒了一次装配**（工具提议第一轮的第 3 发）。端点回 HTTP 200 却一个字没吐、
  零个提议，我把它按「正常收尾」装配，`Check()` 那句「原话 0 字节、0 个提议，却记成了正常收尾」
  直接整发拒收，`被拒的写入 1 次` 上了 tally。**拒得对，改的是调用方**：
  现在那一发记成 `malformed_action` + 一句只含量数的说法 + `retry_after_ms` 如实缺席。
- **读侧第一次被拿来下判定。** `kernel.read_back` 把第 3 发的 `model_says_sha256` 从账上读回来，
  与第三方按同一规则本地重算的一致 —— 之前这本账只被写、被验链，没被用来做过一个结论。

  `truncation-notice` 段发出去）—— `Cuts` 与通知四格第一次由真数据填上。

### 2.6 把这本账供出去给别人读（`cmd/kaudit`，只读）

审计者要问的三件事都在账里：**链自洽吗**、**每一格是谁算的**、**某一发某一侧到底记了哪些话**。
`cmd/kaudit` 就是把一份已经落盘的 `.jsonl` 账本用 HTTP 供出去，别的机器拿 `curl` 就能读。
它住在 `cmd/` 而不是内核里，因为 `package kernel` 不 import `net/http`、不写磁盘（§6 那条依赖方向）。

```sh
"C:/Users/Admin/sdk/go/bin/go.exe" build -o "%TEMP%\kaudit.exe" ./cmd/kaudit
"%TEMP%\kaudit.exe" -listen 127.0.0.1:8788 -journal 报告/样例-agent.jsonl
curl -H "Authorization: Bearer $KAUDIT_TOKEN" localhost:8788/v1/verify
```

口令只从环境变量 `KAUDIT_TOKEN` 读，绝不进仓库、绝不进账本。**绑非回环地址又没给口令 ⇒ 拒绝启动**，
而不是先起来再等人发现（`kaudit_smoke.sh` 的 C 段实测：退出码 1，理由印在脸上）。

它**没有任何写入口**。这条判定刻意与口令无关：

| 请求 | 回来的是 | 实测（`报告/kaudit-实测-1015-094953.txt`，curl 自己印的码） |
|---|---|---|
| `GET /v1/verify`（带口令） | 三态里的那一个 + 比对过原像的条数 | 200，`✓ 链自洽（共 294 条，其中 294 条比对过原像）` |
| `GET /v1/verify`（网段地址、没口令） | 一句拒绝，账本内容一个字不给 | 401，84 B |
| `POST /v1/read_back`（**带**口令） | 「这个服务只读：没有任何写入口」 | 405，118 B |
| `POST /v1/read_back`（不带口令） | 同上，**不是** 401 | 405，118 B |
| `GET /v1/read_back?call=1&side=output`（少 session 轴） | 点名缺哪个轴 | 400，96 B |

最后那两条是一回事的两半：一发的身份是 **session + 发号 + 侧**，少给一个轴就会把两本不同
session 的同号同侧并成一次回答；而写请求如果先吃到 401，审计者读到的是「配上口令就能写」——
**只读与鉴权各管各的**，谁也不许替谁说话。

「链是绿的」不等于「每一格都对得上原话」，所以拿一份**没有原像**的账（`PayloadOmitted`）供出去时，
读数必须是第三种答案（`报告/kaudit-实测-1015-094953.txt` 的 F 段，真进程里的原文）：

```
{"checked":0,"entries":294,"state":"undecidable",
 "text":"— 字段级自洽（共 294 条，其中 0 条比对过原像）；核不了：294 条没有原像……"}
```

外壳的 10 条测试（`go test ./cmd/kaudit`）不是终点：`tasks/probe/kaudit_probe.py` 有 **8 根针**，
每根抹掉上面的一条承诺，看点名的测试红不红 —— 本轮读数 `RED-ONLY-NAMED 7`，两根对照（干净树全过、
认得出「测试没跑起来」）都成立，读数归档在 `报告/外壳针-7根-1015.txt`。
这 8 根**不在**内核那张针表里（封板时 76 根，10-15 傍晚加 `m83`/`m84` 之后 78 根）：那张是内核判据表的针，
判据 48 键 / 49 格 2026-10-15 已冻，外壳是封板之后新长的面，
所以它有自己的针表和**自己印出来的**汇总。

还没验的一件事：从**另一台机器**真的连过来。本机绑网段地址、带口令、`curl` 打得通（B 段），
但 Windows 防火墙的入站规则没动过 —— 别人连不连得进来取决于那条规则，不在这里写死。

### 2.7 挂成一个会话能直接叫的 MCP（两种传送，一个 owner）

`cmd/mcpkernel` 说 stdio（宿主起进程、走 stdin/stdout），`cmd/mcphttp` 说 **streamable HTTP**
（只会填 URL 的界面、或另一台机器上的调用方）。**协议只有一份**，住在 `mcpsrv/`：
方法名、10 个工具、每一句回话的措辞。两处各写一遍的话，改了一边另一边没改，
调用方拿到哪一套取决于它怎么连上的——而那个差别从读数上看不出来。
搬家这次是**拿存档读数证的**，不是嘴说：`tasks/mcp/drive.py`（`checks=27 red=0`）与
`报告/三分钟接上.txt` 两份，搬家前后逐字节 `diff` **为空**。

起服务（只绑回环）与挂载值：

```
"C:/Users/Admin/Desktop/微内核/微内核/.bin/mcphttp.exe" -listen 127.0.0.1:8797
名称 agentkernel   类型 streamable-http   URL http://127.0.0.1:8797/mcp
```

三条边界都是判据级的，每一条都有一根针能让它红：

- **方法与鉴权各管各的**：非 POST 一律 405（`Allow: POST`），与口令无关；GET 额外说清
  "不给 SSE 流"，否则客户端会挂在一个永不返回的请求上等流。
- **口令只从环境变量 `AGENTKERNEL_TOKEN` 来**，比对用定长时间；**非回环绑定没口令 ⇒ 拒绝启动**——
  这一面**有写入口**（`record_call`/`load_journal`），和只读的 `kaudit` 不同，
  没有口令等于任何人都能往链上记账。
- **一条请求 4 MiB 上限**：`load_journal` 的 `text` 是整本账，不设上限等于让局域网里
  任何人用一条请求把这台空载只剩几百 MB 的机器打死。

**三颗部署开关（10-18 深夜加的，全部默认关 = 现状一字不变）**

| 怎么开 | 开起来是什么行为 | 不开（默认） |
|---|---|---|
| `AGENTKERNEL_REQUIRE_TOKEN=1` | 把"只绑回环就不用口令"这个信任假设关掉：不带口令的请求**连内核的门都到不了**（401，且 401 的响应体里不许有账本内容）。若同时 `AGENTKERNEL_TOKEN` 是空的 ⇒ **503** 并明说"这道闸等于没上"——宁可拒服务，也不要"看着有闸、其实没闸" | 非回环必须有口令（`checkListen` 拦），回环免口令 |
| `AGENTKERNEL_APPEND_ONLY=1`（HTTP 面）/ `-append-only`（stdio 面） | 服务面**不提供换账本这条路**：`load_journal` 一律拒（进"门口挡下"那一笔，链上一条都不动）。`encode_journal` 照旧可用 —— 否则连"先归档再换账"这条唯一正路也被堵死了。要读旧账：另起一个进程去读那份文件 | `load_journal` 可用（替换整本），但链上有条或六笔计数非零时必须点名 `acknowledge=replace` |
| `-max-entries N`（**两面都有**） | 这本账最多写多少条。到顶后 `record_call` 一条都不写、`load_journal` 也不许换进更长的文件；这类拒绝进门口那一桶，并在 `tally` 里单独披露子集「其中容量挡下 M 次」（子集不是第七笔数，不相加） | `0` = 不拦。横幅与 `tally` 都印「没设」（`0` 有两种读法："不拦"与"一条都不许写"，渲染收敛在 `mcpsrv.CapWords()` 一处） |

一句要写在接入处的信任口径：**默认状态是"回环 = 本机可信"**。这一面有写入口，而 `actor`、`session`
都是调用方自报的字符串 —— 链只证明"写下来的没被动过"，**证明不了"是谁写的"**。
要把它当不可信边界对待，就同时给 `AGENTKERNEL_TOKEN` 和 `AGENTKERNEL_REQUIRE_TOKEN=1`。
上面每一条都配了反臂测试（"默认关 ⇒ 现状照旧"与"开了 ⇒ 该拒的拒"各一条，见
`cmd/mcphttp/guard_test.go`、`mcpsrv/review_fix_shell_test.go`）；三颗开关的现状都由横幅自印
（`条数上限 …，只增=…，口令=…`），不用猜起起来的那台是哪种。

真挂上之后从**工具面**叫的读数（`报告/工具面挂载实测-1015.txt`，每条都是工具自己回的）：

kernel.record_call → 整发落账 49 条（输入侧 20 格 + 输出侧 29 格），链上共 49 条
kernel.record_call → 整发拒收（累计 2 次）：内容额度记的是 28835，而按公式该是 32768 —— 这条公式有了第二个 owner

要留住得调 `kernel.encode_journal` 拿字节、由调用方写盘（内核自己不写盘，见 §6）。
**还有第二种红法，比进程死难发现得多**：进程活着、端口还在听、直连 HTTP 一切正常，
而会话里的工具面回「没有连接中的 MCP 服务提供这个工具」—— 因为**连接**被服务端按时关掉了，
客户端不重连。这一面早期的 `IdleTimeout=120s` 就是干这个的：MCP 客户端的连接闲置时长不是"网络慢"，
是"两次对话之间的间隔"（分钟级），于是界到点杀的是我们自己的挂载（10-16 实测：同一根 keep-alive
连接闲置 30 秒照常回话、闲置 130 秒 `ConnectionAbortedError [WinError 10053]`；子代理那边报的是 `ECONNRESET`，
同一个形状的两次独立观测）。现在界给到 30 分钟量级，慢连接那一族仍由 `readHeaderTimeout` 守 ——
**别用踢自家客户端下线的方式去守连接**。这条由 `TestServerTimeoutsAreSet` 钉数值量级
（不是只钉"非零"——上一版只钉非零，正好放过了 120 秒这个杀手），针是 `h9`。
起、查、收用 `tasks/probe/mcphttp_up.sh up|status|down`：`up` 撞到已有监听就**拒绝起第二个**
（两个进程各持一本账，那不是并发，是两本账），`down` 按监听套接字的 owner 收，
收不掉就非 0 退出，并自己印 `残留监听数=0`。

还有一条今天落地的判据是从这一面撞出来的：**空账不再戴 ✓**。新进程第一次叫 `kernel.verify`
回的是 `— 尚无账可核（共 0 条）：这条链上什么都还没核过 —— 别把它读成通过`，
`kernel.tally` 回 `账 0 条（一格都没记过 —— 这不是各档都是 0，是还没有账）`；
只读外壳供空账时 `state` 是第四种词 `nothing_to_audit`。实例、四个方向的测试、`m83`/`m84` 两根针
与"没堵的那一半"（`Verify()==nil` 仍不是通过证书）都在 `报告/已落地-空链不许打勾.txt`。

## 3. 三条规矩（每条都配一个真发生过的反面）

### 规矩一：缺席 ≠ 0，忘了填 ≠ 缺席

三件事必须长得不一样：**量到了 0** / **没量到** / **忘了填**。

反面（真事）：非流式那一发的「分帧数」被写成 `0`。读的人看到的是「一帧都没收到」，
而那恰好是协议错的判据 —— 它真正的意思是「这一发压根不分帧」。

所以流式那三格（分帧数、首帧等待、最大帧间等待）在非流式那一发**必须是缺席**，
写数就拒收；反过来流式那一发报缺席也拒收。两头都有判据。

`Measure` 就是这个三态的载体：**谁算的**（`Basis`）与**有没有**（`Absent`）两根轴刻意分开住 ——
合成一个枚举的话，「没量到」就只能长成 0。

这条规矩一直延伸到**账本上**：缺席不只在 `Measure` 里要和 0 分开，落进那道哈希链时也必须和 0 分开。
所以 `Basis` 专门有 `absent` 这一档（`BasisAbsent`）—— 它既不是 `unset`（忘了填，门口就拒），
也不是 `measured` 的 `0`（量到了、就是零）。而且缺席这一档**必须带理由**：
一个说不出为什么的缺席，与「忘了填」在账上就分不开了，而这一档存在的全部理由就是把这两者分开。

### 规矩二：一个键名只许住一个量

反面（真事）：证据源那个仓库里，`bytes_out` 这一个键名装了两个量 ——
请求侧是「装配后的内容字节」，响应侧是「真过网线的请求体字节」。
实测差过 **6327 → 11570**（JSON 框架与转义膨胀）。
两个数共用一个名字，于是任何按键名扫账本的分析层都会把它们加成一堆，
而账上没有任何一格能说出它们不是一回事。

所以这里叫 `content_bytes` 与 `wire_bytes_out`，两个名字。
`bytes_out` 这个名字被一条判据单独点名禁掉 —— 它的缺席本身就是判据，
不只是「撞名 0 处」的一个特例。

撞名怎么判：每格带着自己的**字段路径**。两侧都有 `call`，字段路径同为 `Call` ⇒ 同一个量，不算撞；
两个字节量若共用一个键名，字段路径不同 ⇒ 当场撞出来。

### 规矩三：一份定义只有一个 owner，而且 owner 要被复核

反面（真事）：`Budget` 是导出结构体，注释写着「只能由 `DeriveBudget` 造出来」。
而注释不是判据 —— 手搭一个 `ContentCeiling = 999999` 的预算，`Check()` 一路放行。
那条公式事实上有了第二个 owner。

所以现在 `InputMeta.Check()` 会把公式**重算一遍**并比对，手搭的那一份进不了门。
同一族还有几处，各只有一个 owner：裁剪分档表（`CutLists`）由 `CheckCutLists()` 自己核；
「指纹必须是 64 位十六进制」只有 `checkFingerprint` 一处（早先在输入侧与输出侧各写了一遍，
而两份拷贝里只有一份被测试守过）；token 口径的白名单只有 `usageOK` 一处，
`Check` 与 `TokenTotal` 都从它读。

## 4. 框架那一侧要做的三件事

内核不认识框架，所以有三件事只能由框架做：

1. **装配与调用**。内核只记账，不装配、不发请求。
2. **落盘**。字节的格式住在 `journal.go`（见 2.1），但**把那些字节写到哪里**仍然是框架的事 ——
   内核交出去 `[]byte`、吃进来 `[]byte`，一行都不碰磁盘。
3. **声明读者**。这是最容易被跳过、也最贵的一件 —— 见下面「已知缺口」第 1 条。

```go
r := kernel.NewReaders()
r.Declare("first_byte_ms", "resume", out.Cells())   // 键名拼错会被拒
report := r.Report(out.Cells())                     // 「N 格里 M 格没有任何声明者读」
```

## 5. 怎么核

### 5.1 快闸：`go run ./cmd/kcheck`

逐节核下面这些事，每节都把自己的分母印出来。一共几节、节号是几，以 `go run ./cmd/kcheck` 自己印的为准（这里不抄一份会漂的数，连清单都不编号）：

- **隔离** —— 递归解析本包每个 `.go` 文件的 import 块，逐条分类；
  工具链够得着时再跑一次 `go list -deps` 交叉核对。
- **键名表** —— 逐侧核 `CheckCells` 的自洽：撞名、幽灵键、死格、两处出处对不上等几类
  （具体哪几类以它自己报红的话为准，这里不抄清单 —— 加一类就会让抄的那份变假）；
  两侧合起来再单独查一次撞名，`bytes_out` 这个名字被直接点名禁掉（它的缺席本身就是判据，规矩二）。
- **裁剪分档表** —— 除「没被挤」外，每个取值必须恰好落进一档，漏一档或落两档都拒；表本身逐档印出来。
- **读者声明表** —— 见「已知缺口」第 1 条。
- **键名表全文** —— 键名 ← 字段路径 ｜ 出处，逐格印出来给人读。
- **元数据到账本的接线** —— 真跑 `record.go` 那道接线：缺依据的写入在门口被拒、且拒收有数；
  `absent` 不带理由被拒（拒因必须点名「理由」，不许恰好被别的规则拒掉也算过）、带理由被收；
  「哪几种出处必须带来源」只有一份判据（闸门够不着那个包内私有函数，
  于是经 `Append` 探它、把名单自己印出来）；`absent` 不可拿去做判定；
  读回来那一半（`CellsOf`/`Keys`/`AbsentKeys`）先喂手工构造的条目核对上，
  再由闸门用**导出的构造器就地搭一份最小合法样例**（两侧各一发，不借 `_test.go` 里的夹具 ——
  闸门不该依赖测试文件；样例搭错了也不会假绿，第一条判据就是「样例自己过得了 `Check`」），
  真跑 `RecordInput` / `RecordOutput` / `RecordCall`：整发落账且链自洽、`Check` 不过或一侧不自洽时
  整发拒收且链上不留半发、**同一发同一侧重记被拒**（`alreadyRecorded` 那道门口）、
  落账的每一条 `Claim` 非空、读回来的键名与键名表逐格对齐。
- **账本的字节格式** —— 真跑 2.1 那一层（全程在内存里，闸门不写磁盘）：没填 `PayloadMode` 被门口拒；
  上面那一本 47 条的账**编出去再读回来**，逐格原样、`ChainReport.Checked` 必须等于条数
  （「比对过」不能靠跳过比对来凑）；换成不带原像再读回来，`Mismatch` 必须是空、
  `NoPreimage` 必须是满的、`Verify()` 那句话里**不许**出现「被动过」而出现在「没有原像」，
  且那份报告的开头必须是 `—` 而不是 `✓`；再反向验一次——改掉一格 `kind`，
  整格 `seal` 必须报红（少了这一半，前一半就只是「一律不比对」）；
  最后从那本不带原像的账**接着记**同一发，去重闸必须看得见旧账。

**「核不了」是三态里的一态，既不是绿也不是红。** 工具链不在 PATH 上时，
交叉核对那一栏会说「核不了」并给出原因，而 import 扫描那一栏的结论照常成立。
但有一个方向刻意相反：import 扫描**连一个源文件都没扫到**时不算「核不了」溜过去 ——
那一路不用外部工具链，扫到 0 个文件说明闸门自己站不住了，那一次计为不过（退出码非 0）。
反面（真事）：证据源那个仓库的闸门在 PATH 上没有 go 的那一次报了 13 项假红，
而「没跑成」与「不合格」在报告里长得一模一样。

### 5.2 慢闸：判据必须能真的红

```
py -3 tasks/probe/kprobe.py <go.exe 路径> <本包目录> <临时工作目录> <报告输出路径> [针名过滤器]
```

它把整棵树拷进临时目录，逐根针制造破坏，并要求每一处破坏都被**点名的判据接住**。
没跑成的针判坏针、不算绿 —— 破坏没落上去（一点都没改到）与拷贝编译不过
（**崩不算红**，测试连跑都没跑）都是这一族。
它支持哪几种针、有几根、每根点名什么去红、这一次红了几条：一律以**它自己印出来的汇总**为准 ——
针的清单跟着代码走，手抄进 README 就会漂，而漂了的清单比没有清单更有害。

最后那个过滤器是**可选**的（逗号分隔的针名子串），只为一种情况存在：锚点漂了。
「锚点命中 0 处」不是判据弱、也不是代码坏，是**针找不到该弄坏的那一行** ——
真发生过：把读侧三个入口加上 `session` 那一轴之后，两根旧针的锚点（写的是加轴之前的那一行）
当轮就报 `ANCHOR-BAD`。修锚点不需要重跑整轮（每根针一趟全量 `go test`），
但筛过的轮子在报告头上会明写「不算整轮结论」，末尾那个「针数」也不再是整轮的分母。

读那份汇总时**先看它自己印的「对照」那一段**，再看针。对照是整轮结论的前提，不是其中几根针：
干净拷贝必须全过（否则那些红可能只是拷贝坏了），而且探针必须认得出「测试没跑起来」
（`go build` 不编译 `_test.go`，所以一个测试文件的类型错误会让 `go build` 照样绿、
而全部 `go test` 针一条判据都跑不了）。任一对照不成立时脚本以非 0 退出 ——
那时满屏的「空针」说的是探针或树坏了，**不是判据弱**。这条歧义真烧掉过一整轮。

退出码现在是四档，别再只问「等不等于 0」：`3` 起跑前被内存闸拦下（**那一次连读数都没有**）、
`0` 干净、`1` 有针没咬住（`VACUOUS` / 坏针 / 崩 / 复验后仍超时）、`2` 对照不成立（那种情况连读数都不可信）。
**`1` 与 `2` 这一条是补的课**：封板轮第一次跑整轮时表里有
2 根 `VACUOUS`，脚本却照样退 0 —— 老代码只对对照失败退 2，`bad` 那一类从来没参与退出码，
于是「有一根针是空的」和「这一轮全绿」共用一个 0。那两根针的病因写在 `报告/封板报告-v1.md` 第 8 节，
一句话：**夹具给了一份永远会被别的判据拒掉的输入，而断言只看「被拒了」不看「谁拒的」**。

内存闸（`KPROBE_MIN_FREE_MB`，默认 900 MB）在**动任何文件之前**问一次 Windows 要可用物理内存，
不够就退 `3`，且不写报告文件 —— 拦下的说明落在 `<报告路径>.not-run`（带后缀，谁也不会读成一轮的结论）。
代价要说明白：这台 4 GB 的箱子在会话里空闲只有 ~600–740 MB，默认阈值今天**是拦得住的**；
要跑就明确压低阈值再跑，报告头上第一行就是脚本自己印的
「起跑前内存闸：可用 X MB（阈值 Y MB）—— 放行」，那句留着，就是「这一轮在拥挤机器上跑的」这个标记。

还有一类是 `TEST-HANG`（每步都带 `KPROBE_TIMEOUT` 上限；曾经有一根针让整轮 47 分钟不落地，
而 `copytree`/`rmtree` 这种 python 自己的步骤不在 `subprocess` 的超时管辖内）。
**超时不再直接算判据的账**：脚本自动把超时的针单挑复验一次（同一份落针代码、同一条上限），
接得住就在汇总里按复验结论记账、行尾标「/ 单根复验」，接不住才留在超时档、参与「这一轮不绿」。
这两支都是逼出来验的 —— 逼法是拿脚本的 Temp 副本注入一句「第一趟一律记成超时」
（那个开关不在仓库的脚本里），再把 `KPROBE_TIMEOUT` 压到 5 秒让复验也真超时；
两次读数（`RED-ONLY-NAMED 1 / 单根复验` 与 `复验仍超时`）原始件在
`报告/稳定性-内存闸-拦下与放行-1016.txt`。
读到 `TEST-HANG` 仍然先看同一份报告里的 `对照 0`：那次 `m43` 报「`go build` 超过 900 秒没回来」，
而同轮 `对照 0` 是 `go test 退出码 124、PASS 0 条` —— 连干净拷贝都编译不完，
那是**这台机器**（4 GB、空载只剩 ~185 MB）而不是代码里的死循环。别把机器读成判据。

### 5.3 外壳自己那两套闸（不在内核那张 78 根的针表里）

同一个规矩：**分母由脚本自己印**。`kaudit_probe.py` 现在报 8 根、`RED-ONLY-NAMED 8`，
`mcphttp_probe.py` 现在报 **22 根**、`RED-ONLY-NAMED 22`（`报告/外壳针-MCP面-22根-1016.txt` —— 那一份里

差的三支正是 #41/#43 这两轮真加进来的测试函数，事前用 `grep -c '^func Test'` 数到 25（mcpsrv 14 + mcphttp 11）

但它照出了我两处自己的错（`s12` 钉在零调用者的死封装上、`s18` 钉在一行永远不被通知测试触达的代码上，

**判绿那行代码自己也改了一次**（就在 22 根这轮）：以前 `bad` 集合里没有 `RED-WIDER`，
所以"红得比点名宽"的轮次照样在末尾印「无空针、无坏针」并**退出 0** —— 这条口径一直只写在文档里、
没写进判绿的那行代码。现在 `RED-WIDER` 并进 `bad`，绿话改成「无空针、无坏针、无宽红」。
**这几份里记着两根先报宽了的针**：`s14`（把"认表头"写宽成"永远丢第一行"）第一轮共红 4 条、

它们不并进 5.2 那张表是因为那张属于已冻的内核判据表（10-15 傍晚起 78 根），外壳的针塞进去只会让 §7 那份凭据更早作废。
`mcphttp_probe` 跨两个文件（`mcpsrv/mcpsrv.go`、`cmd/mcphttp/main.go`），每根针后按原字节修回，
**收尾再比一次树干不干净**，不干净整轮不算。它第一轮报过 2 根 `BUILD-BROKE`——那是我的 mutation
把代码改坏了（删掉 `if` 的初始化语句、把唯一用到 `strings` 的那行抹了），**不是判据弱**；
探针把「编译坏了」和「空针」分开报，正是这一族唯一可接受的失败方式。
冒烟脚本收进程只按**监听套接字的 owner** 收（`netstat` 反查 PID），末尾自带一条
`残留监听数（该 0）` 的自检 —— 用 shell 的 `$!` 去 `taskkill` 杀不到 Windows 进程，
那次它报了「没有找到进程」而脚本以为收了，实际留了三个监听在机上。

## 6. 它故意不做什么

- **不做调度、不联网、不执行工具、不写磁盘。** 已经有商品化实现，重做一遍只是多一个依赖。
  「不写磁盘」在 2.1 之后要说得更准：内核现在**拥有字节格式**（`journal.go`，只 import 标准库、
  连 `os` 都没有），但那一步之后仍然没人替框架做事 —— 交出去的是 `[]byte`，落到哪个文件、
  要不要压缩、何时 fsync，全在框架那一侧。
  「不联网」在 2.6 之后也要说清主语：**`package kernel` 一个 socket 都不碰**。
  2.6 那个 HTTP 服务是 `cmd/kaudit`，它只**读**一份已经落盘的账再供出去，
  写路径一条都没有；依赖方向仍然是 框架 → 内核，不是反过来。
- **不把收尾原因归一化成枚举。** 换一家端点就会多出一个我们没见过的值，
  那时「其它」那一档会把一个新形状悄悄藏起来。原样留着，另外单独记「它到底说没说」。
- **不给「一共挤了几段」那个总数。** 折过的还留着原文指纹能核回去，
  整段没进的模型彻底看不见 —— 一个总数会让这两件事互相抵销。
- **不让模型自述的数进合计。** `Total.Add` 直接拒收 `model_says` 那一档：
  那不是「口径弱一点」，是说话人给自己打分。
- **不脱敏。** 擦码器在框架那一侧，内核连它都 import 不到（见下面第 5 条缺口）。

## 7. 与 `runloop` 的关系

字段表**不是发明的**，是从同目录那个已经跑过真端点的仓库里逐格挖出来的，
每一格都点得出它来自证据源的哪个文件、哪个类型或函数：

- 输入侧 ← `runloop/internal/ctxbuf/ctxbuf.go` 的 `Built` / `Part` / `Truncation` / `Budget`，
  预算常数 ← `runloop/internal/loop/loop.go` 的 `perPartShares` / `transportSlack` / `ContentBudget`。
- 输出侧 ← `runloop/internal/provider/provider.go` 的 `Reply` / 故障类别 / `usageOf`，
  落账键名 ← `runloop/internal/loop/loop.go` 的 `recordReply` 与 request cell。

顺手修掉了三处形状缺陷：

1. **`bytes_out` 一个键名装两个量** → 拆成 `content_bytes` 与 `wire_bytes_out`（规矩二）。
2. **裁尾与整段丢弃只落一个计数** → 三类挤压同一张 `Cut` 表，逐项带 ref / 说话人 / 原文字节 /
   留下字节 / 原文指纹。原先只有折叠有逐项账，另两类只剩一句最多点名三段的人话。
3. **对端自报的 token 数被记成「实测」** → 只能记「转述」。分词器在对端，我们数不出来；
   记成实测会让一张成本表看着像我们自己量的。

另外补了两格证据源量了却从不落账的：端点自报的模型 id、每一发模型原话的指纹
（后者是「线路上没有第三方见证」那个缺口的前一半）。

6. **`go test -race` 在本机不可用**（需要 cgo，本机没有 C 编译器）。

10. **`failure.kind` 与 `failure.status` 有互核 —— 但那条互核把真 401 挡在门外（2026-10-13 已落地：换成一张 `MayCarryStatus()` 表）。**
    先纠正我自己写错的话：这一条本节一度写着「这两格互不复核」，**那是错的**，
    判据在 `output.go` 的 `Failure.check()` 里，是双向的两条：`kind=http ⇒ status≠0`、
    `kind≠http ⇒ status=0`。把它撞出来的是一发故意的假 key：端点回 **HTTP 401**，
    我按 `FailConfig`（取值表写的就是「密钥错」）装配，整发被拒，原话是
    「config 不是 http 那一类，却带着状态码 401」。
    所以今天开着的是三件事，方向和早先写的正好相反：
    - **4xx 那一类故障装不下自己的状态码。** `FailConfig` 那三种成因（密钥错、模型名不存在、参数非法）
      在 HTTP 上**全都带 4xx**，而只有 `http` 那一档许带数。于是一条真 401 要么把码丢了记 `config`，
      要么为了留住那个数改口记 `http` —— 后者会把 `RetrySame()` 翻成 true，
      等于在账上写「原样再发一次有用」，而它只会再吃一次同样的 401。
      中间那一轮我就是这么记的：把一发真 400 记成 `http`，**内核收下了**。
      所以这条互核挡得住「config 带码」，挡不住「把 config 谎报成 http」—— 类别是调用方自己填的，
      而那一格没有第二根轴能反证它。
    - `fail_detail` 的出处**跟着状态码走**（`Status≠0 ⇒ relayed`，否则 `measured`）。
      所以记 `config` 时把对端原话抄进去，那一格会被标成「我们量的」——
      一句对端的话读起来像自己的结论，正是它旁边那条判据想防的事换了个方向发生。
    - 现在调用方的记法是：`config` 那一发的 Detail 只写**我们自己构造的判定句**（标 measured 名副其实），
      状态码写在那句话里，对端原话留在调用方日志、不进账。代价是那个数**住在散文里**，
      而「红不了的承诺是散文」是这份 README 的标题级规矩。
      要改的方向也明确，两条选一：把互核放宽成「收到了对端响应的那几类都能带码
      （`transport`/`budget` 压根没收到，继续不许）」并让 `fail_detail` 的出处跟着同一根轴走；
      或者把「对端回的 HTTP 状态码」做成与 kind 无关的一格。
      **2026-10-13 已落地（第一条那种）**：`Failure.check()` 里那两条按类别的互核删掉了，
      换成一张 `FailKind.MayCarryStatus()`（`http`/`config`/`protocol`/`malformed_action` = 收到过对端响应，
      才有码可记；`transport`/`budget` 没有），与 `RetrySame()` 同住 output.go 一处定义；
      `fail_detail` 与 `fail_status` 两格的出处都跟着它走 —— 后者不再写死 `BasisMeasured`，
      于是"没故障的那一发也报称量到状态码 0"这个形状**从根没了**（在册 27 发全是那个长相）。
      实测前后对照与红的一批读侧断言：`报告/挤历史-判生死.md` 第 6 节、`报告/封板报告-v1.md`。
